# Участие в разработке

Спасибо за интерес к Chat Context Exporter.

## Ключевое архитектурное правило

Проект является DOM-only / network-passive экспортером.

Изменения не должны добавлять механизмы, которые:

- делают самостоятельные запросы к API AI-сервиса для получения истории;
- перехватывают или подменяют `fetch`, `XMLHttpRequest` или `WebSocket`;
- извлекают токены, cookie или другие учетные данные для сетевых запросов;
- используют закрытые endpoints сервиса;
- обходят Same-Origin Policy, CSP или ограничения iframe;
- модифицируют запросы или ответы самого веб-приложения.

Допустимая модель работы:

1. найти доступный DOM-контейнер;
2. прокручивать его через стандартные DOM-свойства;
3. ждать штатной реакции страницы;
4. читать только те элементы, которые страница отрисовала в DOM;
5. локально нормализовать, дедуплицировать и экспортировать данные.

## Адаптеры сервисов

Специфика каждого AI-сервиса должна находиться в отдельном адаптере в `src/adapters/`.

Адаптер может знать:

- признаки определения сервиса;
- селектор scroll-контейнера;
- селекторы сообщений;
- роли сообщений;
- стабильные DOM-ID;
- DOM-маркеры начала и конца истории;
- корневой узел содержимого сообщения;
- timestamp, только если он явно и надежно присутствует в DOM.

Адаптер не должен содержать методы вида `fetchHistory`, `getAccessToken`, `requestConversation` и аналогичные сетевые механизмы.

## Общий код

Общие компоненты должны оставаться независимыми от конкретного сайта:

- прокрутка;
- Collector;
- логирование;
- настройки;
- панель;
- DOM -> структурированная модель;
- exporters.

Не следует накапливать селекторы разных сервисов в одном универсальном файле.

## Экспорт

Сборщик не должен формировать Markdown напрямую. Сначала формируется нормализованная структура сообщения, после чего отдельный exporter сериализует ее в конкретный формат.

Это позволяет добавлять HTML или другие форматы без переписывания адаптеров и Collector.

## Логи

Технический лог не должен копировать текст диалога. В нем допустимы только диагностические метаданные, необходимые для воспроизведения ошибок.

## Проверка изменений

Перед публикацией изменений рекомендуется:

1. проверить синтаксис всех измененных JS-файлов;
2. проверить валидность `manifest.json`;
3. убедиться в отсутствии новых `host_permissions`, если они не были отдельно обоснованы;
4. убедиться, что в код не добавлены самостоятельные сетевые запросы;
5. проверить остановку через `×`;
6. проверить автосохранение и ручной `Save As`;
7. проверить технический лог;
8. проверить длинный чат или дополнительный проход, если менялась логика Collector/scroll.

## Стиль изменений

Предпочтительны небольшие изолированные изменения: один этап -> проверка -> следующий этап.

При добавлении нового ассистента сначала создается отдельный adapter и тестируется определение контейнера/границ/сообщений. Только после надежного сбора подключается экспорт.
