# Кандидат 1.4.1 — увеличение повторов, интервал прокрутки, подсказка HTTP 429

Дата: 23.10.2026. База: полный исходный кандидат 1.4. Состояние: **CANDIDATE / BROWSER ACCEPTANCE PENDING**. Стабильный Baseline: 1.2.

## Входные данные

- По журналу 23.10.2026, запуск «№ 1 AEG», кандидат 1.4 завершил оба прохода: 17 страниц и 168 сообщений в каждом; `CHATGPT_PASS_MERGE added=0 conflicts=0`, Markdown сохранён за 11 минут. Настройки оператора: 10 повторов, базовое ожидание 10 секунд, прокрутка 5000–10000 мс.
- Один HTTP 429 был получен на **побочный дублирующий начальный** GET-запрос. Он корректно не прервал текущую цепочку курсоров; раньше этот случай не сопровождался визуальной подсказкой о нагрузке.

## Новый контракт

| Параметр | По умолчанию | Допустимый диапазон |
|---|---:|---:|
| `errorRetryCount` | 10 | 1–25 |
| `errorRetryBaseSeconds` | 10 с | 1–60 с |
| `minDelayMs` | 3000 мс | 100–60000 мс |
| `maxDelayMs` | 5000 мс | 100–60000 мс |

Задержка перезапуска попытки `N` равна `N × errorRetryBaseSeconds`. При 10 попытках с базой 10 с задержки: 10,20,…,100 с (суммарно 550 с без загрузок). При 25 — суммарно 3250 с (54 мин 10 с), поэтому высокие значения полезны при длительном rate limit, но могут существенно увеличивать время операции. Счётчик общий для 403/429/500 и восстановимых сетевых сбоев, сбрасывается только при начале нового прохода. Продолжается полный текущий проход заново, незавершённые страницы не смешиваются с сохранёнными полными проходами.

Пара настроек прокрутки задаёт случайный интервал между `minDelayMs` и `maxDelayMs`, а не тайм-аут HTTP-ответа. Нижняя граница 100 мс сохранена для ручных настроек. Предустановленный темп нового кандидата — 3–5 с. При обновлении уже сохранённые значения остаются прежними; чтобы принять новый пресет, пользователь нажимает «По умолчанию».

**Любой HTTP 429 для текущего диалога** устанавливает `sawHttp429=true`: панель показывает «HTTP 429: увеличьте задержку прокрутки в настройках». Даже при успешном продолжении сканирования подсказка остаётся видимой, пока работает сессия. Дублирующий начальный GET вне ожидаемой цепочки не расходует retry-бюджет и не вызывает reload. HTTP 429 на **необходимом** запросе вызывает штатную паузу и повтор.

## Приёмка оператором в браузере

1. Установить 1.4.1, открыть настройки и проверить новый пресет через «По умолчанию»: 10 / 10 / 3000 / 5000.
2. Экспортировать «№ 1 AEG» с 1 дополнительным проходом. Ожидаются полные курсорные цепочки, `PASS_COMPLETED` для обоих проходов и сохранённый Markdown. Одна HTTP 429 на побочном запросе не должна прекращать проход.
3. При HTTP 429 убедиться, что обе версии панели (в том числе после reload) выводят краткую подсказку. Подсказка не должна подавлять сообщение о состоянии текущего прохода.
4. При 403/429/500 на необходимом запросе проверить переход `waiting-http-retry` с увеличением задержки 10/20/30… с и корректным отображением «N из 10» (либо установленного максимума до 25).
5. При исчерпании повторов после сбоя первого прохода с ранее сохранённым HTML-tail лимитного диалога убедиться в создании аварийной копии последнего ответа, а при сбое второго — в сохранении полного первого прохода с предупреждением.

Статические тесты **не подтверждают** реальную браузерную приёмку или эффект настройки задержек на частоту ответов 429. Последний зависит от поведения сервера ChatGPT и сети.
