# CANDIDATE 1.3 — контролируемое восстановление после HTTP 429

**Статус:** CANDIDATE / BROWSER ACCEPTANCE PENDING.  
**Основа:** опубликованный baseline 1.2.  
**Дата:** 18.10.2026.

## Диагностика

В двух браузерных журналах `№ 8 AWF` наблюдались повторяющиеся ответы HTTP 429 во время продолжительной генерации. Ошибки на посторонних запросах начального JSON игнорировались штатно. Во втором запуске первичный проход принял восемь страниц (82 сообщения), затем получил HTTP 429 на ожидаемом `/messages?before=...`; прежняя версия переходила в `ERROR` и не создавала файл.

## Логика 1.3

1. Только HTTP 429 на **текущем ожидаемом запросе** запускает охлаждение; сообщения вне курсорной цепочки остаются диагностическими и не прерывают захват.
2. Разрешён ровно **один** повтор 429 за проход; промежуточные принятые страницы и завершённые предыдущие проходы остаются в памяти сессии. Не создаётся и не сохраняется частичный Markdown.
3. Пауза составляет не менее **120 секунд**. Заголовок `Retry-After` (секунды или HTTP date) учитывается, если доступен. Если требуемая пауза превышает 900 секунд, автоматическая попытка не выполняется; оператор получает сообщение. В это время расширение **не нажимает кнопки и не выполняет запросы к API ChatGPT**.
4. После паузы — один штатный `Page.reload`. Начальный JSON и ранее принятые страницы приходят через стандартные запросы интерфейса. Они последовательно сверяются по `requestBefore`, обеим границам курсора и содержимому; сохранённые записи не дублируются.
5. Содержимое начального tail может измениться, если за время ожидания завершился ответ ассистента: при сохранении курсоров заменяется только этот tail актуальной версией. Изменение более ранней страницы или самих курсоров — `HTTP_429_CHECKPOINT_MISMATCH` и отказ от объединения.
6. Следующие новые страницы добавляются в ту же строгую цепочку; завершение по-прежнему требует `hasPreviousPage=false`. Повторный 429 — конечная ошибка; если основной проход уже был успешно завершён, прежний fallback дополнительного прохода сохраняет полный основной результат с предупреждением.
7. Отмена во время паузы убирает запланированную перезагрузку. Серверные ограничения не обходятся быстрыми или бесконечными повторными запросами.

## Важные границы

- Сохранение checkpoint действует **внутри текущей сессии браузера/расширения**, без гарантии восстановления при перезапуске Chrome или потере service worker. Постоянная база данных частичных сообщений не создаётся.
- Для сверки браузер должен снова получить ранее принятые страницы обычной прокруткой; это не моментальный переход к восьмой странице и не добавление ручных API-запросов.
- `Retry-After` доступен не при каждом HTTP 429; при его отсутствии используется 120 секунд. Повторный отказ не игнорируется.
- Проверены локальные тесты и синтаксис. **Реальный браузерный тест кандидата 1.3 не пройден**, baseline 1.2 и GitHub остаются неизменными.

## Приёмочные сценарии

1. Обычный экспорт без HTTP 429, включая контроль генерации и при необходимости дополнительные проходы.
2. На длинном чате: HTTP 429 на ожидаемом курсоре → пауза → один reload → сверка сохранённых страниц → завершение полного экспорта без дублей.
3. Повторный HTTP 429 или изменение исторического содержимого → явное сообщение, отсутствие неполного `.md`.
4. Во время ожидания нажать «Стоп» → перезагрузка не происходит.
5. Отдельный HTTP 403 по-прежнему восстанавливается согласно baseline 1.2, не затрагивая режим 429.
